## What the source contracts already establish

Issue #129 says a Deployment is Workspace-scoped and its immutable revision identifies Package Revision(s), capability projection, selected/allowed Runtime Plan(s), and binding references. It explicitly separates production binding values from package declarations, requires no implicit adapter fallback, pins a resolved snapshot to each Run, preserves the same snapshot on retry, and makes update/rollback affect new resolution without redirecting existing Runs. It says exact table/API names require approved design. Issue #130 makes Package Revision immutable and portable, excludes production credentials, provider URLs, local paths, and executable plugins, requires deterministic capability/runtime-plan identity, and expressly requires package-declared RCC/uv alternatives never to fall back automatically.

PR250's merged `docs/design/deployment-revisions-draft.md` supplies a concrete *proposal* for the missing reference envelope: full PackageRevisionRef, RuntimePlanRef containing package revision + runtime kind + plan digest/schema/compatibility identity, workspace-scoped BindingRequirementRef/BindingReference, and immutable DeploymentRevision/CAS pointer semantics. It explicitly assigns Package manifest/capability/binding requirement/runtime-plan payload/projection syntax to #130, adapter descriptors and dynamic admission to #143, Run/Attempt persistence and the transaction committing a Run pin to #83. It also says #129 can name opaque PackageRevision/RuntimePlan references before those producers are complete. The draft is still marked paused/unapproved; do not describe its proposed names/formulas as accepted implementation or approved syntax without a named owner decision.

The PR250 test `test_deployment_schema_probe.py` is an executable *throwaway proposed-DDL* probe, not a product migration. Its SQLite and PostgreSQL cases check Workspace-composite foreign keys, same-Deployment ancestry/rollback links, Package Revision, binding/provider/worker/policy reference links, current-revision pointer ordering, and rejection of representative cross-scope/missing-reference rows. It does not create or query the product database and does not test object payloads/digest computation, optimistic-CAS concurrency, authorization, resolver behavior, Run snapshot persistence, retry pinning, update/rollback with active Runs, worker selection, or runtime-plan fallback.

Current code confirms those are real production gaps: `Run` in `action_server/src/actions/server/_models.py:80-111` has no Workspace, DeploymentRevision, PackageRevision, RuntimePlan or binding snapshot; no production Workspace/DeploymentRevision/RuntimePlan model exists in the inspected server source. `ActionPackage` remains a mutable directory/environment-hash row at `_models.py:18-37`. The schema probe's two successful tests are design evidence only.

## Cross-architecture disposition

Do not make #130's manifest/schema implementation wait for full #129 CRUD, migration, multi-Workspace, worker-placement, or in-flight Run implementation. That would contradict PR250's explicit `#129`/`#130` ownership split and opaque-reference-before-producer rule. The live issue-level `Depends on: #129` needs a scoped criterion interpretation, not a silent removal or an inference of parent completion.

Smallest predecessor gate for #130 schema work: an architecture owner records acceptance of the already-specified #129 reference envelope at the interface level—PackageRevisionRef, full RuntimePlanRef (package-scoped digest/schema, no package-local string/path), workspace-scoped logical-binding refs separated from production values, and the no-fallback/Run-pin invariant ownership handoff to #83. This is a narrow contract decision; it does not accept PR250's entire paused packet. Once recorded, #130 can define its own immutable manifest, Capability, BindingRequirement, full namespaced RuntimePlan payload, projections, canonical digest schema and golden fixtures against those reference fields. Keep #143 dynamic adapter payload/admission out of this slice. A later #135 compiler consumes the accepted #130 schema; #136 registry/provider and #129's production binding/resolution follow their stated implementation sequence.

If a small #129 production proof is separately desired, isolate it as one local-default Workspace scenario: publish two immutable Deployment Revisions with explicit package/plan refs; prove compare-and-swap on current revision; show a newly created Run pins a revision and a retry retains it after pointer advancement; reject an undeclared plan rather than falling back. Do not pull #83's Run/Attempt storage transaction or #143 admission implementation into the #130 schema slice; coordinate their owners. This would advance #129 but is not a prerequisite to start #130's schema once the interface decision above is accepted.
