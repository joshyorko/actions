# Smaller first functional local-detached profile

Additive design revision; original signed-profile proposal remains unchanged at SHA0663e359b9e3b51e0bcfcc679329fda81d5b646fd00d561771365aaf85eb0717. No implementation or execution. The first slice should explicitly separate content and trust while preserving the current local developer policy. Signed remote/offline deployment ownership is a later separate profile; it is not a prerequisite invented for the current local functional gate.

## Source findings and cold admission

At exact PR30876e7f64a/tree8471f44, normal fresh prepare_runtime always calls publish_artifact then acquire_artifact. publish_artifact currently accepts only environment/provider/runner and does not sign. Previous descriptors originate only from existing imported ActionPackage.env_json in _actions_import.py:180. The deployments PackageRevision types are identity types, not an external Environment Artifact admission API. No supported route was found for a fresh supplied digest to bypass publication. Manually seeding DB/descriptors or monkeypatching publication is not canonical cold acceptance.

Pinned RCC4148c2b7 cmd/environmentPublish.go:57 already defaults publication to its actual local detached trust store and emits genuine provenance, inventory SBOM and fresh revocation snapshot. It supports explicitly selecting --trust-carrier PATH --trust-carrier-type filesystem. Therefore the smallest normal cold flow is to give publish, acquire and exec the SAME explicitly declared filesystem carrier before any operation, retaining the original content provider. No signer, prepublished-artifact path, descriptor injection or state restoration is needed for this existing permissive-local developer fixture.

## Concrete first slice

Production-facing RccTrustProfile initially has only provider-coupled-v1 (default compatibility) and local-detached-v1 (explicit opt-in). Remove unsigned-local-fixture-v1 from this production type; provider-omitted execution belongs only to the stdlib diagnostic runner. Do not add unimplemented signed modes, roots or arbitrary freshness flags yet.

Proposed configuration is ACTIONS_RUNTIME_RCC_TRUST_PROFILE=local-detached-v1 with ACTIONS_RUNTIME_RCC_TRUST_CARRIER=ABSOLUTE_OWNED_STORE. Omitted profile/carrier preserves current behavior exactly. Reject carrier without its explicit profile, local profile without carrier, unknown modes, unsafe or package-controlled paths and contradictory combinations before RCC. The directory must be created/owned by the declared deployment/test owner under an explicit allowed administrative root, not inside selected package source. Validate components, links, containment and writable ownership for publication; never infer this profile from existing files or a failed HTTP carrier. The initial carrier kind is filesystem only, avoiding unsupported half-configurations. Archive/signed roots remain later design.

Add frozen RccTrustProfile(profile_id, carrier_kind, carrier_reference, profile_digest). Both profiles retain --permissive-local for acquire and exec, exactly the current adapter's local policy. local-detached-v1 adds --trust-carrier OWNED_STORE --trust-carrier-type filesystem to publish/acquire/exec. Content --provider remains unchanged in every operation. Centralize trust argument construction, with publication-specific policy flags omitted because env publish does not accept --permissive-local. Do not pass secrets or private signing flags.

The genuine generated carrier is evaluated by RCC: malformed provenance/SBOM/revocations or artifact binding mismatch fails closed; explicit revocation remains rejection. Existing permissive-local disables strict signature and fail-closed freshness requirements already, so do not claim signed remote trust or fresh offline revocation policy. This slice must not change those semantics or introduce a fallback from invalid trust. Provider-coupled default still uses the implicit HTTP carrier and fails503 exactly as today.

Profile changes invalidate reuse and require exact-D trust revalidation as a separately reported preparation class, not an automatic successful cache hit.

Local-ready RCC code verifies local manifest/compatibility/carrier before warm and evaluates carrier again at lease. The content provider can be unavailable without an HTTP trust request because explicit carrier overrides the implicit default; real cold missing-content acquisition still uses the original content provider and may fail. A valid intended local-detached profile can meet #134's configured-provider-unavailable and zero-network functional criteria under the current local developer policy. ## Later signed profile

If a signed deployment profile is later needed, normal cold Runtime publication needs an explicitly configured trusted publisher identity: deployment-owned signing key/key ID, independent consumer public roots, real detached store, and supported env publish --signing-key/--signing-key-id arguments. Private key references never enter persisted descriptor or receipts. The smallest existing code has no prepublished admission path, so either implement this owned signing route or a separately reviewed artifact-binding admission API. Neither is implicitly authorized or necessary for the initial local-detached functional slice.

Canonical doc proposal: Local developer offline execution can use an explicitly declared local-detached profile with RCC's existing permissive-local policy. Select the real owned detached filesystem carrier before publish and pass it consistently to acquire/exec while retaining content-provider identity. Publication generates actual artifact-bound trust metadata; each lease still evaluates that selected carrier and fails malformed/revoked input closed. Preserve default provider-coupled behavior, legacy reprepare and zero-network positive gates. This profile proves local functional behavior, not strict signed remote or indefinite offline freshness acceptance.
