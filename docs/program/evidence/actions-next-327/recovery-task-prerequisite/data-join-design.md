# Ordinary Data join design (read-only audit)

Inspected root 6c67055f5165100b422ce2b6038976041fbb1d79. No implementation edits or tests run. Existing component receipts establish only their stated boundaries; this design is not execution evidence.

## Findings and exact seams

- `foundry/runtime_profile.py:130-228`: authoring projects artifact-verified requirement refs, requires explicit provider selections and exact named operation/schema/effect/bounds equality, then stores BindingAssignment in DeploymentSpecification. This already gives one unchanged Package multiple provider-bound Deployment revisions.
- `deployments/foundry_service.py:208-257`: resolve checks exact retained Deployment snapshot, requirement execute grants and provider execute grants, returning ResolvedDeploymentExecution with capability-scoped bindings. Use this result; never resolve a provider from caller IDs, current default or mutable labels.
- `deployments/foundry_values.py:451-485`: ResolvedDeploymentExecution validates assignment set and immutable revision membership. ExecutionSnapshot itself does not carry generic binding assignments; do not repurpose its invoice-only data_binding.
- `foundry/provider_bootstrap.py:11-42`: startup validates CURRENT against committed SQL, reconstructs catalog seals/config identity, then returns only SqlProviderRegistry. The PrivateProviderStore closes. No configured engine factory or secret resolver survives startup.
- `foundry/provider_catalog.py:421-486`: reconstruction verifies source seals without resolving secrets; resolve_secret is explicit exact-version access. CatalogEntry:76-98 binds config digest to exact descriptor/source/seals. These are the durable reconstruction primitives.
- `foundry/bootstrap.py:235-250,310-317`: configured registry is injected only into RuntimeDeploymentSelection. PinnedGenericRccRunner receives RCC preparation/root only.
- `foundry/generic_execution_port.py:100-119`: runner instantiates GeneratedRccExecution from registry and guarded output service; no logical-operation port. StandaloneActionExecution.current:34-51 and GenericWorkItemExecution._current:161+ resolve immutable bindings but discard them after authorization checks.
- `foundry/rcc_execution.py:115-210,378-445,793-810`: actual generated execution reads immutable Run inputs, verifies Package/schema/plan, records launch intent, extracts source and invokes `action(**inputs)` in prepared RCC. There is no logical data context. _verified_selection does not refuse nonempty bindingRequirements when no logical runtime is available. Requirement-bearing Package format/Deployment compatibility therefore must not be advertised as runtime data readiness.
- `run_outputs/service.py:626-643`: execution_context returns pinned snapshot and inputs under live Attempt fence. stage/publish independently recheck generic Run permissions, not newly introduced provider data.read. The ordinary join must retain this ownership and add logical-read authorization checks at publication.
- `data_queries/sealed_duckdb.py` and `sealed_postgres.py`: already accept authenticated Actor plus exact config/source/registry. They are synchronous read-only components returning bounded canonical bytes with source/operation/contract identities; they do not admit Runs or publish results.
- `run_outputs/detached.py:292` and `foundry/execution_port.py:55` also create GeneratedRccExecution. An optional runtime port must default off on every constructor path, preserving invoice and detached behavior and refusing requirement-bearing dispatch when unavailable.

## Smallest correct initial join

Recommend an explicitly **eager, parameterless scan-context** capability, not a new general RPC service. All selected declared read `.scan/v1` operations are bounded and materialized by the trusted host for the admitted Run before generated Python starts. The generated package reads only its declared logical requirement/operation through an SDK context API. This matches the current engine subset; it does not claim lazy queries, filters, writes or Knowledge. If lazy/parameterized semantics are required immediately, use a separately reviewed request/reply worker channel; do not hide a public HTTP credential-bearing service in this slice.

1. New `foundry/logical_execution.py` with `LogicalExecutionPort.prepare(actor, fence, *, cancelled, deadline) -> PreparedLogicalReads` and `recheck(actor, fence, prepared) -> None`. Host-owned dependencies: deployments, package registry, common outputs, configured provider factory. Resolve exact snapshot's retained Deployment and verify snapshot equality, artifact-derived requirement set, assignments, live execute/provider.inspect/data.read and current provider availability. Only data-kind, read, empty-parameter exact scan operations supported. Reject unsupported requirement/operation before native launch. No caller-supplied worker/provider/policy/contract.
2. `PreparedLogicalReads` holds typed logical-only child context bytes plus host-only receipt refs/source digests/contract digests/result digests and total bytes. Use a reviewed small aggregate bound (proposed256KiB) independent of each operation's limits and a bounded operation count (proposed32). Reject over-bound declared context before fetching, and over-bound actual canonical bytes before launch; never truncate. One total Run preparation/execution deadline, cancellation and both Run/Work Item heartbeat semantics cover all scans, rather than resetting budgets per operation. Unsupported bounds fail closed rather than silently tightening declared semantics.
3. New `actions/src/actions/data/__init__.py` and private context implementation: `scan(requirement_id: str, operation: str) -> list[dict]`, no provider/DSN/path. Empty/unbound context, undeclared names, parameters and unsupported versions reject. It reads an immutable host-prepared context only; no engine, network or credential dependency in SDK. Return a fresh decoded value or immutable representation so an action cannot modify another logical lookup. Context installation is a private runtime hook, not a model/tool argument. New SDK artifact/version must be supplied through canonical compiler packaging; this is an actual cross-package change, not injected test PYTHONPATH proof.
4. `foundry/rcc_execution.py`: optional explicit logical port default None. For zero requirements preserve exact existing helper/launch serialization. For nonempty requirements require port before launch; prepare using current fence and immutable selections, write a private bounded context next to input.json, install SDK context in the helper, and bind context digest plus source/operation receipts to a versioned launch/terminal record. Do not merge data into Run.inputs or action kwargs, and never put private host config/secret material in source, Package, context, model metadata or Run outputs. Eager reads happen before launch intent (safe to repeat only because the subset is read-only over retained immutable bytes); once native launch intent exists, existing uncertain-launch refusal remains unchanged. No fresh Run/Attempt or automatic retry.
5. Recheck logical authority at heartbeat/stage and **inside the existing final SQL publication transaction**, after long RCC execution. Prefer a narrowly composed guard callback on the current domain-owned output wrapper, or an explicitly typed guard supported by GeneratedRccExecution; do not wrap _GenericOutputs in a type that breaks existing require_rcc_selection checks. No second output publication/audit ownership. A pre-publish standalone recheck alone has a revocation race. Stage private provisional output and discard on denied final publication using existing measured ownership rules. Retained historical output download remains governed by existing Run/artifact read policy; data.read is required for a new query, not retroactively invented as an artifact read permission.
6. `foundry/generic_execution_port.py`, `invocation_discovery.py`, `generic_view.py` and pre-dispatch domain paths: expose availability only when exact requirement set/operations are supported and configuration exists. Read-only discovery must not resolve passwords, probe databases or execute scans. Distinguish configured support/authority from successful live execution readiness. Gate before admitting an unsupported new Run where possible; executor remains defense-in-depth. Wire the same trusted port into ordinary standalone and Work Item execution; preserve reviewed invoice route. Detached worker gets explicit optional port or refuses bound capabilities, never a silent default.

## Config reconstruction and lifetime

Add a typed `ConfiguredProviderExecution`/factory alongside existing metadata registry in provider_bootstrap.py. Absent provider-state/CURRENT remains None. Startup verifies saved owner lineage, exact committed catalog/audit and seals, loads only non-secret config DTOs and indexes exact provider revision refs. It does not mint permissions, recover intents, connect to engines or resolve secrets.

At execution open a read-only PrivateProviderStore using saved operator owner/workspace (not caller identity as store owner). Revalidate CURRENT/committed provenance and selected entry against the pinned catalog generation/config digest; missing selected historical provider entry rejects, never remaps to newest. Build SourceSealRecord from that entry and the saved owner. DuckDB needs no secret resolver. PostgreSQL receives a resolver restricted to the exact password/CA references from this verified config; it calls store.resolve_secret only during execute. Store remains open for execution and closes in finally, with each engine connection/temp CA file already owned/closed by adapter. SQL connections remain thread-owned; no provider/network work occurs while holding a common SQL writer transaction.

Catalog updates are offline/operator-mutex-owned in v1. Current startup may hold a validated generation in memory, but each execution must detect private pointer/config changes and fail closed or explicitly reload a wholly validated generation; do not combine a stale SQL descriptor with new private config. Source blobs stay under the existing Runtime source-provider lifetime (`RuntimeCanvas.close`); new manager close cannot close the shared provider twice. Secret rotation creates new immutable private secret/config references and explicit catalog lineage; no environment fallback. Shared PostgreSQL administrative coordination and multi-host private catalog distribution are still separate operational gaps.

## Adversarial and regression tests

- Zero-requirement Package/helper/journal identity unchanged; unavailable runtime port rejects nonempty requirements before native launch; unsupported write/filter/Knowledge declarations are not advertised.
- Wrong selected capability, requirement ID collision, extraneous/missing binding, cross-workspace provider, changed contract bound/type/source/config digest and mutable metadata tampering fail before engine call.
- Revoked requirement/provider execute, provider.inspect/data.read, disabled provider, lost Attempt epoch/lease, queue claim loss, cancellation and aggregate deadline during multi-operation prepare and RCC cause no final publish; test revocation racing publication under both common SQL backends.
- Private resolver call spy: zero startup/discovery calls; exact two PG secret refs on execution; no arbitrary SecretVersion resolution; CA/password failure sanitized even broken logging. No values/paths/tokens in public metadata/journal/context.
- Host context spoofing, child-modified context, wrong digest, reused old Run context, oversized context and repeated mutable SDK lookup do not affect trusted outputs/lineage. Generated Python remains trusted developer code, not hostile code sandbox.
- Crash before preparation, after prepared data but before launch intent, after intent before spawn, worker loss and restart: preserve existing uncertain outcome gate. Read-only prelaunch preparation may repeat; never repeat native action launch or create another scheduler.
- Actual generated package consumes both engine results across >128 rows, nulls/Unicode/NUL and bounded result; no mock-only data proof.

## Risks / decisions needing integration review

Eager context semantics and aggregate bound are new explicit SDK/runtime contract decisions. A new installed SDK artifact changes compiler preparation; root owns versioning/RCC qualification. Data grants must join final SQL publication atomically without breaking domain wrappers. Run receipt/journal version changes need replay compatibility and old-reader refusal for bound execution. Existing provider secret storage bounds CA to64KiB although engine accepts262KiB; retain stricter actual store limit or version it explicitly. No new table/migration appears necessary: Deployment retains assignments, existing journal/output receipts retain run evidence and private catalog retains configuration. Do not pretend that this scan slice completes full Data/Knowledge owner scope.
