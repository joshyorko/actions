## Main correction: two distinct protocol generations

The current official extension identifier is **io.modelcontextprotocol/tasks**, verified at https://modelcontextprotocol.io/extensions/tasks/overview and https://github.com/modelcontextprotocol/ext-tasks. It is not speculative. Current per-request client capabilities and server/discover negotiate it. Use current extension schemas, not the SDK's retained legacy Task DTOs. Current methods are tasks/get, tasks/update, tasks/cancel; successful task creation is discriminated resultType=task. Current Task polling embeds final result/error and interaction requests. There is no current tasks/list or tasks/result. Source of truth for implementation must be a pinned ext-tasks schema commit plus fixtures; SEP-2663 explicitly says its accepted text is historical, not current schema authority.

For 2025-11-25 compatibility, a separate adapter can use installed ServerTasksCapability, ToolExecution.task_support and request task metadata, with get/result/cancel/list. Never advertise these legacy methods on the current wire. #85's list/result product requirements can be met by authorized internal Run listing plus version-specific protocol behavior; do not reintroduce removed current wire operations. Current extension negotiation is not blocked on an owner-invented identifier.

SDK 2.0.0 evidence: mcp/server/extension.py MethodBinding supports protocol_versions and rejects shadowing core methods; lowlevel Server.add_request_handler registers typed RequestParams handlers but does not itself supply extension version gating. Current Actions setup_mcp_server_v2.py uses lowlevel Server, so the smallest wiring is additive handlers plus explicit request-context protocol/capability gates, and current discover advertisement. Do not switch the whole gateway composition layer just for this feature. Add current typed DTOs from a pinned authoritative schema in mcp/task_wire.py, with conformance fixtures; legacy DTO imports remain isolated. Include required routing header/name behavior in transport tests against pinned schema/SDK. Do not install an unpinned extension package.

## Actual implementation gaps

RunOutputService.admit already persists normalized input and immutable admission; claim produces independent fenced RunAttempt and requires explicit recovery before replacing an expired owner. RunPin carries cancellation/recovery state. These are the authority to extend.

Generic and standalone domain dispatch currently admit AND claim AND produce a launch journal for a caller's configured worker. They cannot merely be called from a detached Future and called durable. Split admission from trusted worker claim; preserve current synchronous dispatch as a composition of those same operations. Input-linked generic admission must atomically retain exact input selection and independent claim semantics; an idle long queue cannot hold an unrenewed UI-owned claim.

Existing invoice_worker is a scoped business worker, not a general durable Run selector. Reuse its lease/effect discipline, not InvoiceReview payloads. A common bounded consumer of eligible RunPin/Run rows is a missing execution component, not an MCP Tasks queue. GeneratedRccExecution already heartbeats its Run output authority and polls a cancellation callable during subprocess drain. PinnedGenericRccRunner currently supplies a local Event; replace that input with a SQL-backed cancellation/lease guard for detached consumption. Preparation must gain equivalent periodic observation, not just the subprocess loop.

Legacy _api_robots.py /run inserts run-UUID records and schedules a process-local background coroutine with mutable package paths. It is not canonical RunPin/Attempt admission, immutable capability runtime selection or restart proof. A genuine Robot adapter under the common worker is required; wrapping that HTTP route does not satisfy #85.

## Required boundaries before claiming full #85

Current Run status enum alone does not encode queued reason, confirmed cancellation, business versus infra failure, paused interaction or terminal uncertain review. Add typed common evidence/phase transitions first; do not infer them from strings in result JSON. Task TTL is separate from output expiry; expiry hides Task receipt, does not cancel business execution. Terminal Task status remains immutable; unavailable output produces explicit result-unavailable error, never downgrade completed into a different terminal status or return false available handles. GC may remove payloads only while retaining enough authorized tombstone/retention identity for defined expiry behavior.

Durable interaction/resume is part of #85, not optional decoration. If existing review authority cannot resume common capability execution, implement the binding before advertising input_required/update. Resume and expired-worker retry require existing operator-verified no-effect recovery; ambiguous external effects remain review-blocked. New Attempt retains Task UUID and exact plan. New plan is a new Run/Task.
