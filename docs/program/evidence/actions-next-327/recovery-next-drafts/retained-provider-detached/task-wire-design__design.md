## Current wire: exact shapes and gates

The identifier is io.modelcontextprotocol/tasks. Request _meta must contain io.modelcontextprotocol/protocolVersion=2026-07-28 and io.modelcontextprotocol/clientCapabilities.extensions containing that key, in addition to ordinary authenticated caller context. Server.discover capabilities.extensions carries the same empty object only when a real detached service/worker path is configured. Every Task request rechecks capability declaration; a prior request does not authorize subsequent polymorphic responses. No invented extension settings.

CreateTaskResult.json is FLAT: resultType,taskId,status,createdAt,lastUpdatedAt,ttlMs,pollIntervalMs; no nested task object and no ttl/pollInterval legacy names. GetTaskResult.json is flat resultType=complete plus DetailedTask; completed carries the original operation result inside result. UpdateTaskResult.json and CancelTaskResult.json are acknowledgements containing resultType=complete, not Task status. Pending cancellation is observed through later get; acknowledgement never asserts process stop.

GetTaskRequest.json, UpdateTaskRequest.json and CancelTaskRequest.json contain exact taskId; update also has inputResponses. HTTP requests require Mcp-Method matching method, Mcp-Name equal to taskId, and MCP-Protocol-Version matching the modern request envelope. Core SDK validates method/version; our Task adapter explicitly validates name/taskId because current SDK name routing map is empty. Use SDK decode_header_value rather than ad-hoc decoding. For official client typed requests, subclass Request and set name_param='taskId'; still test raw HTTP missing/mismatch negatives. stdio has no HTTP header requirement. Header routing never substitutes for authentication/workspace authorization and shared SQL removes any sticky-routing requirement.

Nondeclaring current client receives -32021 Missing Required Client Capability with requiredCapabilities.extensions={io.modelcontextprotocol/tasks:{}}; unknown/inaccessible/expired Task uses uniform -32602. Reject unsupported protocol before admission. Current tasks/list and tasks/result are absent. Avoid automatic server cache hints on these methods: task ttlMs denotes lifetime, not a cache validity promise.

## Explicit Actions invocation and acknowledgement contract

Proposed closed model-only capability_invoke argument variant:
{"mode":"detached","snapshot":<exact ExecutionSnapshot>,"inputs":<typed ordinary Action input>,"idempotencyKey":<1..128 UTF-8 bytes>}

This is an Actions operation choice, not a new MCP task flag. It accepts no worker, prepared paths, actor, TTL, queue/claim or arbitrary task ID. Its schema is disjoint from existing reviewed/generic variants. Existing synchronous calls remain unchanged. Modern params.task is rejected for this branch rather than silently treated as a current protocol option. Server chooses the Task shape for this explicitly detached operation only if the request declares the extension. Later declared-long or budget-based automatic escalation is a separate still-open #85 policy, not part of this prerequisite.

Before any mutation, require an explicitly configured DetachedTaskHost backed by the same Database/DetachedActions, trusted exact worker profile(s), prepared verified runtime/adapter path, and an actual installed worker consumption entry point. A disconnected/not-ready worker may yield truthful queued state if the configured path exists; merely constructing receipt DTOs or providing an unused callback does not qualify. No configured path -> bounded server-unavailable error, no Run, no receipt, no acknowledgement. Do not advertise capability if this is absent. Constructor never creates grants, starts a scheduler or derives worker identity from request arguments.

Within one canonical transaction: existing detached admit + request fingerprint + Task receipt insert. Recheck live execution authority on duplicate creation; enforce same actor and exact original invocation/result contract. Existing non-Task detached Run cannot silently become a Task; differing original method/name/TTL-policy identity is conflict. Commit before returning acknowledgement; response loss retries return same Task/Run. No response-shaping memory object owns execution.

## Canonical receipt and lifecycle time (reserve migration21)

Add RunTaskReceipt, unique run_id, in the common SQL database: receipt version; workspace_id; admission principal; original method='tools/call'; original tool name='capability_invoke'; result-contract version; invocation fingerprint; created_ms; ttl_ms (host-chosen positive bounded policy); policy identity. Task ID remains Run UUID. Do not store Task status, Attempt ID, worker location, inputs/source copy, result copy, credentials or transport session. Validate receipt against RunPin, immutable ExecutionSnapshot and intent on every lookup. Authorize get through live common Run read independently of execute; cancel through live cancel independently of read/execute. Keep same-admission-actor constraint for this initial adapter; broader delegated observers require explicit reviewed policy.

TTL starts at durable receipt creation; replay does not refresh it. Receipt expiration does not cancel Run or expire artifacts. Expired/GC receipt maps to uniform unavailable; no re-ack of expired receipt under the same idempotency key (require a deliberate new Run/key). Resolve every required sealed output before claiming available successful result. If output retention lapses, return result-unavailable error, not a fabricated success or a new terminal Task state. Do not change completed->failed on a later read.

Existing common Run/Attempt has no trustworthy exact publication/cancellation timestamp: publish changes state without updating a timestamp, and queued cancellation has no Attempt. Therefore lastUpdatedAt must NOT be the current poll time or a fabricated last heartbeat. Migration21 should also add canonical RunPin.state_updated_ms, initialized at new admission and updated atomically on claim, cancellation intent, queued cancellation and publish; future phase/recovery transitions do likewise. Preserve request/snapshot canonical bytes. For existing non-Task Runs backfill an empty/unknown timestamp and disallow retroactive Task receipt adoption; no fake history required. Task createdAt comes from its immutable receipt; lastUpdatedAt derives from canonical state_updated_ms. This field is common lifecycle evidence, not Task state authority. Keep historical migration15's column/schema compatibility under test when adding a model field.

Projection initial supported states: queued/executing/pre-launch-loss or reconciliation-required -> working with bounded statusMessage; Run PASSED + succeeded matching Attempt + complete resolvable output inventory -> completed with original result; confirmed queued CANCELLED -> cancelled. Running cancellation remains working until authority confirms outcome. Retained launch uncertainty never becomes fabricated failed/succeeded. No synthetic failed mapping: later genuine JSON-RPC execution error evidence is required. Tool business isError=true is completed, not failed. Robot, Work Items and interactions remain excluded from this initial declared subset.

Original CallToolResult is produced by one versioned shared formatter also usable synchronously: bounded model-safe execution receipt and separately authorized output handles. Store its contract identity, not duplicate result bytes. Reconstruct only from sealed Run publication. Current nested result includes its original resultType=complete; legacy result is serialized with legacy CallToolResult schema. Never forward private app session metadata, raw source, local paths or arbitrary persisted execution journal. If formatter semantics change, retain old contract version for old Tasks.

## Minimal lowlevel integration

New mcp/task_wire.py: closed request Params types and released DTOs with exact aliases; preserve RequestParams _meta. Current schemas use ttlMs/pollIntervalMs. New mcp/task_service.py: transactional receipt operations/projection with independent read/cancel permissions; no worker loop. New mcp/task_adapter.py: strict version/capability/header gates and existing MCP caller resolver; method registration.

McpServerSetupHelper.__init__ accepts optional configured Task host. Its _call_tool checks the exact detached variant before routing normal reserved calls; ordinary routing is unchanged. Register current tasks/get/update/cancel via add_request_handler; set server.extensions only after configured prerequisites are validated. Do not replace lowlevel Server or change installed SDK. Core runner already preserves unknown modern resultType, so current creation returns a schema-validated dictionary.

Interactions: never emit input_required or issue inputRequests in this subset. A known authorized ordinary Task has zero outstanding interactions. tasks/update validates bounded InputResponses and ignores unknown/already-answered keys with empty acknowledgement, as the pinned specification recommends; it never adopts arbitrary responses, mutates Run state or resumes work. This is not interaction support. If product scope chooses to reject rather than ignore unknown keys, use a bounded protocol error and document the deviation from SHOULD; preferred design is spec-consistent no-op. Full #85 needs persisted interaction authority and real request/resume tests later.

## Legacy compatibility without weakening core gates

Legacy version=2025-11-25 uses initialize capabilities.tasks, ToolExecution.taskSupport, params.task and wrapped SDK CreateTaskResult, ttl/pollInterval; get/result/cancel/list are version-gated separately. Task identities/receipts remain identical. No current shape leaks onto legacy wire. A modern client never gets legacy operations. Older pre-Task versions keep synchronous-only behavior.

Observed SDK issue: returning wrapped CreateTaskResult directly from on_call_tool fails its normal result serializer. Proposed narrow response-shaping middleware preserves core initialization/typed request validation instead of short-circuiting it: establish a request-local response slot, call_next normally, and let the detached handler commit admission, set the slot, and return a valid internal CallToolResult(content=[]). After successful core handling, middleware replaces only that response with the validated legacy CreateTaskResult. The empty intermediate result is never sent or stored. ContextVar slot is per-request transport formatting only, reset in finally; no global task map. Errors propagate unchanged; missing slot cannot create an acknowledgement. This must be tested for concurrency/cancellation/context leakage in both SDK versions before using it. An alternative SDK-supported legacy custom result hook may replace it only after verified evidence.

Legacy initialize advertisement can be added to the result of successful call_next by version-aware middleware; initialization acceptance remains SDK-owned. Legacy taskSupport applies only to configured eligible tool path. Legacy tasks/result waits on durable SQL terminal state, reauthorizing on polling; transport cancellation stops only the waiter. Never return current working shape as a legacy final result. Legacy tasks/list is bounded authorized receipt listing with separate pagination; it is not worker scan. Add legacy implementation only with real independent client tests; current extension conformance alone does not qualify legacy support.
