# Managed Work Items consumer contract — #132 / #327

This is the canonical Actions-owned handoff to Automation VS Code PR1. It is a
component of the existing release, not another queue, board or release train.
The extension owns UI/LSP and remains a client. It must not open Runtime SQL,
implement leases/retries locally, or infer managed support from FileAdapter.

## Current admission and versions

Published Runtime1.0.4 tag `d222f94edca26953c1506ab258adc458ded17c56`
provides the local SQLite `/api/work-items` CRUD/attachment surface. It does not
provide this authenticated Workspace/Deployment/fence/review protocol.
Published SDK0.4.4 is not the managed fencing floor. Do not call local CRUD a
managed service or fall back to it after a managed authorization failure.

The provisional protocol floor is Runtime1.1.0a13 with installed fenced
SDK0.5.0a1. Neither is a new public release. Exact candidate wheels and producer
receipts are required for installed acceptance; the public index cannot resolve
unpublished candidate versions. The floor may advance with further changed SDK
bytes; every changed built package needs a distinct candidate identity.

Implemented here: closed commands and response models, version/permission
negotiation, bounded authenticated routes and a review-backed common-SQL service.
Ordinary Linux Runtime startup with a native Canvas artifact joins the managed
router to its existing common SQL and owner identity. Other unsupported or
unconfigured hosts remain unavailable unless explicit dependencies are supplied.
The joined service creates no grants: schema discovery can succeed while live
Workspace capability discovery returns403. Mounting does not authorize a queue
or configure a complete managed execution profile.
Default-profile configuration, installed consumer and VSIX acceptance remain
required. No denial falls back to legacy local CRUD.

## HTTP and wire schema

- `GET /api/managed-work-items/v1/schema`: authenticated contract export.
- `GET /api/managed-work-items/v1/capabilities?workspace_id=<uuid>`: authenticated
  installed versions, actually available operations/modes and explicit grants.
- `POST /api/managed-work-items/v1/operations`: one closed discriminated command;
  response has `schema_version`, `operation`, `runtime_version` and typed `result`.

The immutable protocol name is `actions.managed-work-items/v1`. Source models
are `actions.server.managed_work_items.contracts`; the generated export is
[`managed-v1.json`](../contracts/work-items/managed-v1.json). Each named command
or result schema is a standalone JSON Schema document with local `$defs`.
The export and live `/schema` are generated by `public_contract_schema()`.

`QueueRef` contains `workspace_id`, exact `deployment` revision and opaque
`queue_id`. It is not a filesystem path, database URL or credential. The scope
is checked against the actual binding before access. Existing admitted work
retains its revision; a new current head does not silently rebase that work.
Mutations carry `idempotency_key`; interventions carry `expected_epoch` and a
reason. Server reconciliation and retained receipts decide uncertain outcomes.
A client timeout is not proof of failure and never authorizes changing the key,
recreating a Work Item or performing an automatic external-effect retry.

These permissions are necessary, not sufficient. Every operation also checks
live Workspace/queue scope and existing admission, review, Run/output and
artifact grants. Work Items review permission does not replace the exact-result
Run `review` grant. Visibility, a handle, owner UUID or epoch is not authority.
The authenticator supplies `ManagedCaller(actor, worker_id)`; caller JSON cannot
supply either. Claims derive the owner from authenticated worker context.
Renew/complete require that same owner plus current queue/item/epoch and DB-time
lease. Lease requests are 1–3600 seconds, matching SDK validation.

ItemView keeps queue state, business outcome, claim, exact admission snapshot,
protected input digest, parent/child IDs and Run IDs distinct. Claim loss is not
business failure. Unknown business outcomes remain explicit. A pending review
is a ReviewView with no manufactured Work Item. RunView retains separate
Attempt identities, owner/epoch/deadline, result and scoped artifact references.
The service must compute the Work Item payload fingerprint using the canonical
SDK helper; the original query-input digest remains a separate Review binding.

Only actually supported/authorized operations may be advertised. A queue's
permissions further narrow workspace discovery. Direct enqueue requires its
declared capability mode and policy; reviewed enqueue cannot create an approval.
Review decisions delegate the retained exact binding to the existing review
service. Completion/publication must use existing dual fences and actual
Run/Attempt evidence, not trust client output claims. Retry requires verified
no-effect/idempotent/reconciled evidence and bounded policy. Unknown effects
remain blocked for reconciliation; terminal dead-letter replay is not an
unconditional reset or an adapter switch. No generic exactly-once claim exists.

Errors are bounded codes:401 unauthenticated,403 forbidden,404 not found,
409 stale claim/changed input/approval required/uncertain effect/unsupported,
413 byte limit,422 invalid request and503 unconfigured/storage unavailable.
Provider SQL, paths and exception details never appear in responses. Command
and response bounds are512KiB; item/log pages and output lists are bounded.

## SQL service and trusted host integration

The implemented constructor is
`SQLManagedWorkItemsService(reviews: InvoiceReviewService,
authorization: QueueAuthorizationPort,
worker_for: Callable[[CanvasResultScope], InvoiceWorkerService | None])`.
The optional worker lookup is keyword-only. It implements ManagedWorkItemsPort
in `managed_work_items/sql_service.py`. Derive queue references from validated
existing InvoiceReview binding scopes and
`reviews.queue(scope).queue_name`; never enumerate/open arbitrary files or
create a queue database. Use the existing common SQL FencedWorkItem, Review,
Run/Attempt and output services. The authorizer is integration-owned and live;
worker selection is trusted host configuration, never command JSON.

Public service calls own `Database.connect()` in their executing thread. An
ambient connection in the caller's thread does not cover FastAPI's synchronous
worker thread and otherwise produces a bounded storage-unavailable response.
Capabilities require live READ before looking up workspace scopes. Claim/renew
replay rechecks authorization, owner/epoch/state/cancellation and DB-time expiry,
then returns the current deadline/server time; it preserves the original stored
request, claim identity and single audit record.

`SqlQueueAuthorization` requires explicit `work_items.*` grants in the common
SQL authority for both Workspace and exact Deployment reference. These do not
replace the source review/Run/output grants. `bearer_authenticator` maps an
explicit host credential to one server-configured Actor/worker pair; headers
cannot choose either identity. The Runtime perimeter delegates only this exact
managed prefix to that authenticator and continues protecting other APIs with
their existing policy. This adapter does not create credentials or grants.

Evidence-bound completion delegates to the existing invoice worker after actual
RCC execution. The wire `queue_state` is `DONE` when the SDK's persisted state is
`COMPLETED`; do not change the SDK/storage representation to match a transport
label. Repeated completion returns the retained item and replay flag, without
another execution. Client-provided output payloads and Run IDs are not execution
evidence.

First prove real queue/item/review/claim/lease/Run/artifact inspection,
review/cancel delegation and denial/revocation/isolation/restart. Delegate
supported mutations to existing SDK/review/worker methods, retain their
transactions and exact receipts, and advertise only proven operations.
Do not invent completion output, retry absence or dead-letter evidence. Leave
unimplemented operations unadvertised and report exact missing dependencies.
This bounded adapter is not full #132 completion: general queue modes,
not-before/fairness/fan-out, remaining retry/review semantics and actual installed
VSIX acceptance stay explicit current-release work. No side store or second
scheduler is authorized.

## Native generated Run inspection

Native reviewed Work Items project their existing Run/Attempt and final bounded
RCC stdout/stderr outputs through the same managed read routes and output
resolver. Log pages contain at most100 bounded lines from finalized attached
objects, with deterministic stdout/stderr ordering; artifact byte reads keep
their separate permission. No raw local-file fallback exists. Claim epochs and
Attempt epochs are independently validated against their canonical rows. A
reclaimed Work Item can legitimately have claim2 and first Attempt1. Cancelled
or lease-lost native projection currently fails closed; inspectable recovery
status and general producer/retry semantics remain release gaps.
